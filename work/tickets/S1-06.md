# S1-06 knc-twin multi-core check of gravity on the large case (8 cores on the ring)

Sprint 4. Depth: light. Starts after S1-05 is merged (it reuses S1-05's gravity region, cut at the error branch until
gcc-knc S14-20 lands). knc-twin 0.4.0 at ~/.claude/skills/knc-twin; read `references/handoff-prompt.md` and the
`unit`/`ring` scale text in SKILL.md first. Multi-core results are implemented, not validated: every number here is an
`unvalidated_scenario_estimate`, and the doc must say so.

S1-05 found the 1-core gravity `bounds` (43,656) above `simulate` (33,622) on the same kernel: an open twin defect,
reported to the knc-twin session. So use `simulate` and `compare` only, report the change from 1 to 8 cores rather
than absolute cycles as the finding, and repeat that caveat in the doc.

## Question
Does the gravity kernel keep its per-core speed when 8 cores (32 contexts) walk the large case's tree at once, or do
L2 misses, the ring and the memory controllers slow it down? The large case (20k bodies) no longer fits one core's L2;
the medium case does and is not part of this ticket.

## Do
1. Inputs from the measured run: capture the large case's bodies and tree at one force step with the S1-03 capture
   tooling (`twin/prepare_capture.py`, `twin/capture_log.c`) from the x86 reference build, as `init.memory` file
   blocks. Same card binary and gravity region as S1-05.
2. Unit of work: forces for one contiguous slice of bodies, split the way the program's OpenMP loop splits them at
   240 threads (read the loop's schedule clause; state it). Each context gets its own slice; use the same slice size in
   every configuration, so cycles per body are comparable.
3. Run `simulate` with the same profile (`card-7120-measured`) for:
   a. `--scale core`, 1 core, 4 contexts;
   b. `--scale unit`, 8 cores x 4 contexts (`streams[].core` places them);
   c. `--scale ring`, 8 cores x 4 contexts with the synthetic background of the remaining active cores.
   Use `sample-loop` if a slice is too long to simulate in full, and say so. Keep each run under 30 minutes of host time.
4. `compare` b and c against a. Report cycles per body per context, L2 miss rate, and the ring/memory stall share from
   `result.json`, plus `assumptions`, `unsupported` and `parameters_used` entries that are `assumed` or `derived`.
5. Write `docs/twin-multicore.md`: the table, the result class, what the twin does not model (only 8 detailed cores;
   the rest are background traffic), and what the card run can check later (60 vs 240 threads on the large case,
   S1-04's card commands). No card access, no claim about the card's speed.
