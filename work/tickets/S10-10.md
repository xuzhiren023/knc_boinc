# S10-10 Fill every core with vector work in star setup (exact decisions, batched integrals)

Sprint 10. Depth: deep. No card access (the lead runs card jobs). Host load cap: 4 cores. Starts after S10-09 lands
(same files); build on its `DF_VECTOR8` kernel (libknc_vmath log/atan accepted by the owner: card likelihoods
identical).

## Why
Card, core-small (window 19:42Z): exact release 54.3 s, `DF_VECTOR8` 57.3 s, guard 57.3 s, likelihood identical.
The vector kernel is slower because the parallel work shrank: one integral has ~330 quadrature nodes = ~42 8-lane
vectors, but the card has 60 cores x 4 threads, so per integral only ~42 threads get work and ~200 spin; the card
draws ~137 W (scalar-class). Integrals are evaluated one at a time because each body's work is a serial chain:
`max_finder` golden-section steps, then rejection attempts (2.56 per body on average, up to 39), with the dSFMT
stream consumed in order.
Owner 2026-11-17: give each core the right amount of vector arithmetic to keep its instruction issue full without
polluting the cache.

## Design targets
- Enough independent vector work per core: a KNC core issues one vector instruction per cycle and needs at least two
  hardware threads to issue back to back; with ~4-cycle latencies, aim for at least 4 independent vector chains in
  flight per core (e.g. 4 threads x 1-2 chains). For 60 cores that means roughly 240-480 vectors in flight at once,
  i.e. about 6-12 integrals evaluated concurrently, not one.
- Working set per core inside L1 (32 KB per core, shared by 4 threads) for the node data of the integrals it owns,
  and well inside L2 (512 KB): node positions, coefficients, partial results; model parameters read-only.

## Do
1. Exact sources of concurrent integrals (decisions and the RNG order unchanged):
   - Rejection attempts: draw the next K attempts' (v, u) pairs from a copy of the dSFMT state, evaluate their K
     integrals concurrently, take the first accept in order, and advance the real state by exactly the draws used
     (S8-05 has the save/restore mechanics). Choose K from the attempt distribution (mean 2.56).
   - `max_finder`: speculate the next golden-section points (both branches, 2-3 levels deep), evaluate their integrals
     concurrently, keep the ones the original comparisons select (S10-03's pipeline idea, widened).
   - Combine both so the card always has ~6-12 integrals in flight; count wasted speculative integrals.
2. Scheduling: assign whole integrals (or contiguous vector blocks of one integral) to a core's 4 threads together
   (core-aware binding, threads 4c..4c+3 on core c; check GCC-KNC libgomp's default spread order: siblings are
   t, t+60, t+120, t+180), so the node data of one integral stays in that core's L1. Model the per-core working set.
3. knc-twin: the vector node kernel on one core with 4 contexts, 1 vs 2 vs 4 independent integrals per core: cycles
   per node and the issue/occupancy constraint it reports; record predictions before the card run.
4. Proof: core-small and real-steps generated bodies compared with the exact build (count differing bodies), card
   likelihoods vs exact (must be identical to accept), and host timing at 4 threads.
5. Card binaries (release options + `DF_SPECIAL=1 DF_VECTOR8=1` + this option), knc_lint, a window script with
   `--transfer tcp-large` (core-small, real-steps), predictions recorded first.

## Accept
- Concurrency/waste counts, working-set model, twin results, proof output, binaries, window script and the Effort
  line in the Engineer report.
