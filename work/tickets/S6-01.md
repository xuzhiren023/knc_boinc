# S6-01 Prototype: gravity tree walk with one body per vector lane, bit-exact, twin first

Sprint 6 (owner 2026-11-16: "yes" to option A). Depth: deep. No card access. knc-twin at ~/.claude/skills/knc-twin.

## Why
`nbGravity` (`nbody_grav.c`) walks the threaded tree for one body at a time: `q = root; while (q) { far or body?
interact, q = Next(q) : q = More(q) }`. GCC-KNC computes it on x87, one operation at a time (`x87_serial` binds in the
twin). KNC's 512-bit unit holds 8 doubles: 8 bodies can walk the tree in lockstep, each lane following its own `q`,
with masks for lanes that open a cell, interact, or have finished.

## Hard rules
- **Results stay bit-identical**, on x86 and card. Each lane must do exactly the scalar code's operations for its
  body, in the same order: same opening test, same `eps2` choice, same `mw_sqrt`, same quad terms, same summation
  order into `acc0`, same self-interaction and tree-incest handling. No FMA (`-ffp-contract=off`), no reassociation,
  no `-ffast-math`, no approximate reciprocal or rsqrt. Vector add/sub/mul/div/sqrt on KNC are correctly rounded,
  which equals x87 at 53-bit precision except for subnormal/overflow range: say whether that range can occur here.
- No IMCI intrinsics (GCC-KNC has no header yet; ADR-0013 in gcc_knc). Write portable C the vectorizer can map: a
  restructured loop over 8 lanes with if-conversion, or GCC vector extensions (`vector_size(64)`). Prefer the form
  that also compiles for x86 unchanged, so the x86 reference build runs the same code.
- A patch in `patches/`, selected by a build macro (default off = upstream code); the card build turns it on only
  after this ticket's evidence, and that switch is the lead's call.

   the tree built once per step: cost and memory), lane bookkeeping (refill a finished lane with the next body, or
   keep groups of 8), how masks keep per-lane order identical, and where divergence costs. Read GCC-KNC's
   `docs/USING.md` and `docs/gcc-knc-flags.md` for what the vectorizer supports (masks, gathers, `-fopt-info-vec`).
2. Implement behind the macro. Show from `-fopt-info-vec-optimized` and the disassembly that the walk uses `zmm`
   (masked) operations, not x87.
3. Exactness on x86: small, medium (1 and 12 threads) and large (12 threads) with the macro on are bit-identical
   to the references (`scripts/compare.py`, plus the histogram files), and the S1-06 per-body accelerations of the
   first 4,096 large bodies are identical byte for byte.

   Baseline: the scalar `nbGravity` for the same 8 bodies via the S1-07 compiled chunk driver. If the scalar

   alone and mark the comparison as waiting for S14-37; never report timing from a mismatching run.
