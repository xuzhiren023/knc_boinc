# S10-08 TCP upload path for our card_run; fix the recovery tool's card check

Sprint 10. Depth: light. No card access by the engineer (the lead runs card jobs). Host load cap: 4 cores.

## Why
Owner 2026-11-17: "if DMA doesn't work use TCP". Today DMA failed three times (helper deadline, cleanup uncertain)
under laptop load and latched the card for both projects; ssh uploads run at ~20 KB/s (a 48 MB job takes ~40 min).
Lead measurement 17:34Z: the card pulling a 32 MB file from a host socket with busybox `nc 192.168.1.99 PORT > file`
received all 32,323,605 bytes in under one second. Card busybox 1.19.4 `nc` has no `-l` (client only), so the card
connects to the host. Host mic-side address: 192.168.1.99 (Ethernet); card 192.168.1.100 (mic0).

   publish step. Integrity: byte length only (owner rule: no checksum on host-card transfers). Downloads (collect) may
   stay ssh unless large.
2. Transfer policy: `auto` = files below the threshold by ssh, larger by DMA; if DMA is unavailable before an endpoint
   opens (preflight), use TCP instead of ssh. After DMA data starts, an uncertain cleanup still stops and latches

   entirely while the laptop is loaded. Document both in tools/CARD_RUN.md.
3. Fix `tools/card_dma_recover.py`: its card check failed with exit 2/255 while a plain ssh check worked (17:30Z);
