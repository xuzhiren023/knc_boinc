# S8-03 Parallel quadrature nodes in the mixed-dwarf body generator (results bit-identical)

Sprint 8. Depth: deep. No card access. Deadline: a card binary within 75 minutes of start (card window closes 02:59Z).

## Why
S7-02 measured the real workunit 117676 (110,000 bodies, `Dwarf.plummer` + `Dwarf.cored`, `predefinedModels.mixeddwarf`)
on the laptop: our x86 12-thread run took 5,488 s, and evolution only began at about 4,560 s (live step samples in
`.work/S7-02/build/live-step-samples.jsonl`: step 999 at 5,151 s, step 1460 at 5,423 s, 1,568 steps). About 83% of the
real task is serial body generation (`nbGenerateMixedDwarfCore`, `nbody_mixeddwarf.c:909`). One card thread runs this
x87 code about 10x slower than a laptop core, so on the card it would take many hours. The dominant cost is
`dist_fun` (`:465`) -> `gauss_quad` (`:94`): about 110 intervals x 3 calls of `fun` (`:364`), each about 30
potential/density evaluations; `vel_mag` (`:587`) calls `dist_fun` in `max_finder` and in every rejection attempt.

## Why this can be bit-identical
`gauss_quad`'s node positions come from a serial recurrence (`lowerg`, `upperg`, `coef1`, `coef2`, the switch to `Ng =
10` after `benchmark`) that does not depend on `fun`. `fun` depends only on its arguments if `get_potential` and
`get_density` (`nbody_dwarf_potential.c`, `nbody_density.c`) have no hidden state: check this and say so. So: run the
same recurrence first to record every node and `coef1`, evaluate all `fun` values in parallel into an array, then
accumulate `intv` serially in the original order with the original expression
(`intv = intv + c1*f1*coef1 + c2*f2*coef1 + c3*f3*coef1`, left to right), keeping the `counter > 100000` exit and the
sign flip. The random number stream, rejection decisions and every body are then unchanged.

### Implementation and purity

- Added `patches/nbody-parallel-quad.patch`, off by default through
  `NBODY_PARALLEL_QUAD=0` / make `PARALLEL_QUAD=0`. The card build script and
  patched x86 test build explicitly enable it. A make configuration stamp
  rebuilds the generator object when the option changes in an existing OUT.
- Retained the original serial routine as fallback. The enabled routine
  records the original recurrence's three nodes and coef1 per interval,
  retaining the decimal constants, benchmark/Ng transition, termination
  checks including `counter > 100000`, and sign flip. Only independent
  callback evaluations run in an OpenMP static parallel-for. The barrier
  precedes serial accumulation with the original left-associated
  `intv + c1*f1*coef1 + c2*f2*coef1 + c3*f3*coef1` expression. There is no
  reduction or moved RNG/body sampling. Normal intervals use a small stack
  buffer; unusual intervals grow a private heap buffer. Allocation failure
  restarts the serial routine. `omp_in_parallel()` callers run serially.
- Purity finding: 1.96 dispatchers are **not unconditionally pure**: NFW/cored
  can call `set_model_params` when p0 is zero; King can initialize when r_0
  is zero. `get_density`, like `get_potential`, is actually defined in
  `nbody_dwarf_potential.c`; `nbody_density.c` defines external-potential
  densities, outside this integrand path. The generator already initializes
  both models and recalculates masses serially before sampling. Plummer and
  initialized cored evaluations only read model fields/arguments. Derivative
  and incomplete-gamma paths use local variables; `gammln`'s only static data
  are a const coefficient table. There is no RNG, mutable cache or model
  write on that initialized callback path. The patch allows Plummer/general
  Hernquist and NFW/cored with nonzero p0; other/uninitialized profiles stay
  serial so lazy writes cannot race.
- Kept `-ffp-contract=off` and x87 setup. `main` calls `nbSpecialSetup` /
  `crlibm_init` before workers are created. Card disassembly still loads
  0x027f with `fldcw` (53-bit, nearest). The supplied libgomp `team.c` creates
  workers with `pthread_create`, inheriting the parent's floating-point
  environment; the same pool is reused for force loops. Test hooks checked
  every x86 worker: parent 027f, zero mismatches in all four runs. Card
  inheritance is confirmed by startup/runtime code inspection, not hardware
  observation.
