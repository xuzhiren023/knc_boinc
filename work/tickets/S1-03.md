# S1-03 knc-twin check of the N-body force kernel (pre-card validation)

Sprint 1. Depth: standard. Depends on S1-02 (merged). Owner 2026-11-15: use the knc-twin skill for card validation.

## Why
The card is shared and often busy. The knc-twin skill (C:/Users/xuzhi/.claude/skills/knc-twin, read its SKILL.md and
`references/validation.md` first) simulates one KNC core: it can check that the compiled hot kernel computes the same
values as the x86 reference and predict its cycles. It does not run whole programs; the card gives the final answer.

## Do
1. Find the hot function of `small` on x86 (Cygwin `-pg`/gprof or another tool you have; say which). Expect the
   gravity/force calculation.
2. `python scripts/knc_twin.py capabilities` and check that every mnemonic in that function of the card binary is
   supported. Unsupported or timing-only mnemonics are a result: report them, do not approximate.
3. Extract the whole function from the card binary with `scripts/from_binary.py` (objdump from the K1OM binutils);
   costed stubs only for callees you cannot include, with the cost source stated.
4. Record real inputs: from an instrumented x86 run of `small`, dump the inputs of one call (bodies/tree nodes etc.) and
   its outputs as the expected values. Feed them as `init.memory` file blocks.
5. Run `validate`, `functional` (expected = x86 outputs, tolerance stated) and `simulate --profile card-7120-measured`
   and `bounds`. Put each run's `result.json` + `summary.md` under `twin/` and write `docs/twin-check.md`: verdicts,
   `result_class`, assumptions, unsupported items, and a predicted per-call cycle figure the card run can be compared to.

## Acceptance
- `docs/twin-check.md` states plainly whether the compiled kernel matched x86 in the twin, with the twin's status
  fields copied, and every number labelled with its result class.
- Scripts in `twin/` rerun the twin steps from the built binary.
