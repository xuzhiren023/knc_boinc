# S2-01 Spike: BOINC API built with Cygwin g++ against the Windows BOINC client protocol

Sprint 2. Depth: standard. Network: yes (fetch only). Decision D4 in docs/PLAN.md.

## Why
The wrapper must be a Windows program the Windows BOINC client can control. The laptop has only Cygwin g++ (with the
w32api headers), no MinGW or MSVC. Decide early whether a Cygwin build of the BOINC API speaks the client's protocol.

## Do
1. Extend `scripts/fetch.sh` with BOINC (https://github.com/BOINC/boinc) at a pinned recent client release tag; record
   it in `SOURCES.md`. Fetch only; build only `lib/` and `api/` pieces the app side needs (boinc_api, graphics2 shmem
   helpers, filesys, parse, util, shmem, ...).
2. From the client source, write down exactly how the **Windows** client talks to an app: shared-memory mapping name and
   size, `SHARED_MEM` layout, message channels, quit/suspend handling, how it finds the graphics shared memory, any
   mutexes/events/handles (cite file:line). Then show which Cygwin build variant (plain POSIX Cygwin, or `-mwin32` /
   `_WIN32` paths with the w32api headers) produces an app side that uses the same names, layout and calls.
3. Prove it without installing BOINC: a small test-only "fake client" built from the client's own code for that
   protocol (or a faithful minimal copy, cited) that creates the shared memory as the Windows client does, starts a
   test app built with your variant, sends `<suspend/>`, `<resume/>`, `<quit/>`, and reads `<fraction_done>` and
   checkpoint messages. Also run the test app standalone (no client) to show standalone mode works.
4. If no Cygwin variant can match, stop and say so with evidence: the fallback (portable MinGW-w64) is the owner's call.

## Acceptance
- `docs/boinc-api-on-cygwin.md`: the protocol facts with citations, the chosen variant, the test result, the
  runtime DLLs the app needs (e.g. cygwin1.dll) and the remaining risk against the real client.
- `make -C mk boinc-api` builds the library; `tests/` has the fake-client test, and it passes.
