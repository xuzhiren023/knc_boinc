# S10-07 Tree walk memory behaviour: spatial body order and huge pages (forces bit-identical)

Sprint 10. Depth: deep. No card access. Laptop load light. Use knc-optimize (model first) and knc-twin (one core with
4 contexts, and the 8-tile ring mode for cache/L2 sharing effects; multicore is an unvalidated estimate).

## Why
Window 8 (runs/card/w-knc8/): the tree walk (`nbGravity`) takes ~3.05 s per thread on the large case, close to the
memory-latency model (~2.9 s all-cold), and the twin's one-core result for it is 148,351 cycles/body. The force loop
(`nbody_grav.c:340`, `for (i = 0; i < nbody; ++i)`, `schedule(dynamic, 4)`) visits bodies in generation order, which
is spatially random, so the 4 threads on a core, and consecutive chunks on one thread, walk unrelated parts of the
tree and share little in L1/L2. In-place prefetch and a hot-field layout (S10-02) gave nothing.

## Ideas (exact; each behind its own option, off by default)
1. Spatial order (`WALK_ORDER=1`): after the tree is built, take the bodies in threaded-tree order (the order the
   walk's Next links visit them) as a permutation, and run the force loop over that permutation; each body's force is
   still computed by the same walk with the same arithmetic and stored to its own slot, so results are bit-identical.
   Give each core's 4 threads neighbouring work (contiguous chunks, or a core-aware static/dynamic split) so they
   share tree nodes in L1/L2.
2. Huge pages (`WALK_HUGEPAGES=1`): back the tree pool (S8-07 pool) and the body array with 2 MB pages if the card's
   kernel allows (madvise/THP or hugetlbfs; check what MPSS offers), to cut DTLB misses (twin assumes a 64-entry
   4 KB DTLB, 29 cycles per miss).
3. Anything the model points to, e.g. copying the per-body position into a compact array read by the walk.

## Lead note (card huge-page state, checked 2026-11-17)
Card kernel 2.6.38.8+mpss3.7.1: transparent huge pages are already `[always]` (enabled and defrag), page size 2 MB;
the hugetlbfs pool is empty (`nr_hugepages=0`; mounts at /mnt/huge and COI2MB exist). So prefer 2 MB-aligned
allocations of the tree pool and body array (posix_memalign 2 MB, sizes rounded up to 2 MB) plus
`madvise(MADV_HUGEPAGE)`; no reserved pool is needed. Verify in the card job by printing `AnonHugePages` from
/proc/meminfo (or /proc/self/smaps) while the force loop runs. Do not change kernel settings from the app.
