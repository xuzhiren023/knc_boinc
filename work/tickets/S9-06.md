# S9-06 Parallel, exact partition for the balanced tree (tree bit-identical)

Sprint 9. Depth: deep. No card access. Laptop load light: `make -j2`, identity runs on small/medium/large at 1 and
12 threads only.

## Why
Card, large case, S9-04 `TREE_VARIANT=3` (runs/card/w-knc2/large.txt): nbMakeTree 7.08 s of a 20.95 s run, of which
`tree_partition` 5.93 s runs serially on one card thread; everything else is now small (insertion 0.10, CofM 0.15,
Quad 0.21, threadTree 0.55, expandBox 0.13). Removing most of the partition time takes the large case to ~15-16 s,
below the best x86 build (18.0 s).

## Design (exact)
A body's octant at each level comes from `nbSubIndex` comparisons against the cell midpoint, and a cell's midpoint
comes only from its parent and the octant (`nbInitMidpoint`/`calcOffset`). So each body's octant path can be computed
independently, in parallel, with the same comparisons the serial code makes (descend from the root midpoint, as
deep as the frontier needs, at most the epsilon depth). Then a stable parallel sort (or counting sort per level) by
path groups the bodies exactly as the serial stable partition does, preserving body order within each group; the
frontier and upper cells follow from group counts. No position quantization or Morton bits from coordinates: only
the serial code's own comparisons.

## Do

2. Identity: the every-build tree identity checker on small, medium, large at 1 and 12 threads;

3. Card binary `build/s9/card-tree4/milkyway_nbody.mic` (S9-04's card options with `TREE_VARIANT=4`); knc_lint; the

- Added `patches/nbody-tree4.patch`, class Performance, selected only by
  TREE_VARIANT=4; the default remains 0. It extends S9-04's variant 3, retaining
  its max(2, nbody/(4*threads)) frontier cap and epsilon stop. Variant 3 retains
  its original partition. expandBox already has the exact max reduction and
  variant 4 uses it.
- At each level, independent contiguous 64-body tiles compute octant paths
  using nbSubIndex against the actual parent cell midpoint. Per-group integer
  prefixes assign each tile's output range in original tile order. Each tile
  scatters bodies in original local order, giving a stable parallel counting
  sort, including stable removal of zero-mass bodies. No position quantization,
  coordinate-derived Morton bits, floating reduction or arithmetic replacement.
- Upper cells still use nbMakeCell/nbInitMidpoint/calcOffset. The cell list is
  reversed from breadth order to child-before-parent order; each cell's own
  octant arithmetic is unchanged. Insertion, CofM, Quad and Next/More boundary
  repair use variant 3's code. One persistent OpenMP team handles all partition
  levels; upper-cell creation and level metadata remain serial. Group/tile
  buffers have nbody+1 slots and are retained/released with the pool; the upper
  cell list retains variant 3's dynamic growth for long unary chains.
- Rebased the separate Instrumentation patch onto variant 4 and enabled its
  existing checker/frontier diagnostics for both variants. No instrumentation
  hooks were added to the Performance patch. patches/README.md names both
  classes. Complete and correctness-only pinned-source replays pass.
- Added build/test/staging helpers and two acceptance tests: the six-run tree
  identity/science proof, and the card handoff/prediction. The handoff manifest
  binds the card binary, patch files, build options, runtimes and window script.

Prediction, recorded before any card run: large partition ~0.916 s over 111
builds, down from the ticket's measured 5.93 s. Model:
5.93*(0.05 + 0.95*2/24) + 0.15. Assume 5% serial upper-cell/metadata work,
2x parallel work per visit to allow prefix/scratch traffic, 24 effective workers
(10% of 240 hardware threads), and 0.15 s total dispatch overhead. At 12/48
effective workers the estimate is ~1.385/~0.681 s. Holding other measured
subphases fixed gives nbMakeTree ~2.066 s and whole run ~15.936 s. The retained
prospective 240-thread frontier samples come read-only from the required
12-thread snapshots; variant 4 has variant 3's exact frontier. Full samples,
assumptions and prediction: `build/s9/tree4-model.json` and
`build/s9/tree4-prediction.txt`. No model table was used.

Not proven: native 240-thread identity/results, card timing or the predicted
speedup, or full 117676 behavior/performance. Bandwidth, barrier latency, serial
prefixes and long unary paths may change the estimate substantially. Native
measurements remain for the lead's staged card window. No compiler optimization
issue was established: this change is stable partitioning/parallel scheduling,
with no manual vectorization, prefetch, vector math or scalar arithmetic rewrite.
